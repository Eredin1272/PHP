## Описание лабораторной работы

Цель работы - разработать веб-приложение средней сложности с серверной логикой, базой данных, аутентификацией пользователей, защищёнными разделами и административными функциями.

В рамках проекта реализовано традиционное MVC-приложение на Spring Boot. Предметная область - работа клиники: публичный просмотр информации, регистрация пользователей, отправка заявок на приём к врачу и администрирование данных.

Основные требования, покрытые проектом:

- регистрация и вход пользователей;
- безопасное хранение паролей с использованием BCrypt;
- публичная страница с динамическим контентом из базы данных;
- форма создания ресурса с клиентской и серверной валидацией;
- форма поиска;
- защищённые разделы для авторизованных пользователей;
- роль администратора;
- административное управление данными;
- модульная архитектура MVC;
- документация к основным методам.

Дополнительное задание восстановления пароля не реализовано, так как оно не является обязательным.

## Инструкции по запуску проекта

### 1. Требования к окружению

Для запуска проекта необходимы:

- JDK 21;
- PostgreSQL;
- Maven Wrapper, уже включённый в проект;
- база данных `clinic_db`.

Проверьте версию Java:

```powershell
java -version
javac -version
```

Ожидается Java 21.

Если Maven запускается с ошибкой `release version 21 not supported`, нужно указать правильный `JAVA_HOME`:

```powershell
$env:JAVA_HOME='C:\Program Files\Java\latest\jdk-21'
$env:Path="$env:JAVA_HOME\bin;$env:Path"
```

### 2. Создание базы данных

В PostgreSQL нужно создать базу:

```sql
CREATE DATABASE clinic_db;
```

Текущие настройки подключения находятся в файле:

```properties
spring.datasource.url=jdbc:postgresql://localhost:5432/clinic_db
spring.datasource.username=postgres
spring.datasource.password=72582480
```

Перед запуском на другом компьютере пароль и пользователя PostgreSQL нужно заменить на свои.

### 3. Запуск приложения

Из корневой папки проекта `clinic-app` выполните:

```powershell
.\mvnw.cmd spring-boot:run
```

Если порт `8080` занят, можно запустить на другом порту:

```powershell
.\mvnw.cmd spring-boot:run -Dspring-boot.run.arguments=--server.port=8081
```

После запуска приложение будет доступно по адресу:

```text
http://localhost:8080
```

или, если использовался порт 8081:

```text
http://localhost:8081
```

### 4. Тестовый администратор

При первом запуске автоматически создаётся администратор:

```text
Логин: admin
Пароль: admin123
```

Начальные врачи, услуги и объявления также добавляются автоматически через `DataInitializer`.

### 5. Проверка сборки

Для проверки проекта выполните:

```powershell
.\mvnw.cmd test
```

## Сценарии взаимодействия пользователей

### Сценарий 1. Регистрация пользователя

1. Пользователь открывает страницу `/register`.
2. Вводит логин и пароль.
3. Приложение проверяет корректность данных.
4. Приложение проверяет, свободен ли логин.
5. Пароль хешируется через BCrypt.
6. Пользователь сохраняется в базе данных с ролью `ROLE_USER`.
7. После успешной регистрации пользователь переходит на страницу входа.

### Сценарий 2. Вход пользователя

1. Пользователь открывает страницу `/login`.
2. Вводит логин и пароль.
3. Spring Security проверяет данные через `CustomUserDetailsService`.
4. При успешной проверке создаётся сессия.
5. Пользователь перенаправляется в личный кабинет `/dashboard`.

### Сценарий 3. Создание заявки на приём

1. Авторизованный пользователь открывает `/appointments/new`.
2. Заполняет форму:
   - ФИО пациента;
   - телефон;
   - email;
   - врач;
   - услуга;
   - дата и время;
   - жалоба;
   - согласие на обработку данных.
3. Браузер выполняет клиентскую проверку обязательных полей.
4. Сервер выполняет проверку через Jakarta Validation.
5. При ошибках форма возвращается с понятными сообщениями.
6. При успешной проверке заявка сохраняется со статусом `NEW`.

### Сценарий 4. Поиск заявок

1. Авторизованный пользователь открывает `/appointments/search`.
2. Указывает критерии поиска:
   - ФИО пациента;
   - врач;
   - статус.
3. Сервис фильтрует заявки по указанным критериям.
4. Пользователь видит таблицу найденных заявок.

### Сценарий 5. Работа администратора

1. Администратор входит под аккаунтом `admin`.
2. Открывает `/admin`.
3. Управляет заявками, врачами, услугами и администраторами.
4. Обычный пользователь не имеет доступа к `/admin/**` и получает ошибку 403 при ручном переходе.

│   ├── DoctorForm.java
│   ├── MedicalServiceForm.java
│   └── UserRegistrationDto.java
├── model
│   ├── Announcement.java
│   ├── Appointment.java
│   ├── AppointmentStatus.java
│   ├── Doctor.java
│   ├── MedicalService.java
│   └── User.java
├── repository
│   ├── AnnouncementRepository.java

Назначение слоёв:

- `controller` - обработка HTTP-запросов и выбор представлений;
- `dto` - объекты форм и валидация пользовательского ввода;
- `model` - JPA-сущности базы данных;
- `repository` - доступ к данным через Spring Data JPA;
- `service` - бизнес-логика приложения;
- `security` - настройка аутентификации и авторизации;
- `templates` - Thymeleaf-шаблоны;
- `static/css` - стили интерфейса.

## Структура базы данных

База данных формируется автоматически Hibernate на основе JPA-сущностей. Используется режим:

```properties
spring.jpa.hibernate.ddl-auto=update
```

### Таблица `users`

Хранит пользователей приложения.

| Поле | Тип | Назначение |
|---|---|---|
| `id` | bigint | первичный ключ |
| `username` | varchar | уникальный логин |
| `password` | varchar | BCrypt-хеш пароля |
| `role` | varchar | роль пользователя: `ROLE_USER` или `ROLE_ADMIN` |

### Таблица `doctors`

Хранит врачей клиники.

| Поле | Тип | Назначение |
|---|---|---|
| `id` | bigint | первичный ключ |
| `full_name` | varchar | ФИО врача |
| `specialization` | varchar | специализация |
| `experience_years` | integer | стаж |
| `office` | varchar | кабинет |
| `active` | boolean | активность записи |

### Таблица `medical_services`

Хранит медицинские услуги.

| Поле | Тип | Назначение |
|---|---|---|
| `id` | bigint | первичный ключ |
| `name` | varchar | название услуги |
| `description` | varchar | описание услуги |
| `price` | numeric | цена |
| `active` | boolean | активность услуги |

### Таблица `appointments`

Хранит заявки на приём.

| Поле | Тип | Назначение |
|---|---|---|
| `id` | bigint | первичный ключ |
| `patient_name` | varchar | ФИО пациента |
| `phone` | varchar | телефон |
| `email` | varchar | email |
| `doctor_id` | bigint | внешний ключ на врача |
| `medical_service_id` | bigint | внешний ключ на услугу |
| `appointment_time` | timestamp | дата и время приёма |
| `complaint` | varchar | жалоба пациента |
| `status` | varchar | статус заявки |
| `created_at` | timestamp | дата создания заявки |

Статусы заявки:

- `NEW` - новая;
- `APPROVED` - подтверждена;
- `CANCELLED` - отменена.

### Таблица `announcements`

Хранит публичные объявления клиники.

| Поле | Тип | Назначение |
|---|---|---|
| `id` | bigint | первичный ключ |
| `title` | varchar | заголовок |
| `body` | varchar | текст объявления |
| `published_at` | date | дата публикации |

### Связи между таблицами

```text
appointments.doctor_id -> doctors.id
appointments.medical_service_id -> medical_services.id
```

Один врач может иметь много заявок. Одна медицинская услуга также может быть связана со многими заявками.

## Примеры использования проекта

### Пример 1. Хеширование пароля

Фрагмент из `UserService`:

```java
user.setPassword(passwordEncoder.encode(dto.getPassword()));
user.setRole(role);
```

Пароль пользователя не хранится в открытом виде. В базу данных сохраняется BCrypt-хеш.

### Пример 2. Ограничение доступа к административному разделу

Фрагмент из `SecurityConfig`:

```java
.requestMatchers("/admin/**").hasRole("ADMIN")
.anyRequest().authenticated()
```

Все маршруты `/admin/**` доступны только пользователям с ролью администратора.

### Пример 3. Серверная валидация формы записи

Фрагмент из `AppointmentForm`:

```java
@NotBlank(message = "Укажите ФИО пациента")
@Size(min = 3, max = 120, message = "ФИО должно содержать от 3 до 120 символов")
private String patientName;

@NotNull(message = "Выберите дату и время")
@Future(message = "Дата и время должны быть в будущем")
private LocalDateTime appointmentTime;
```

Даже если пользователь обойдёт клиентскую проверку браузера, сервер всё равно проверит данные.

### Пример 4. Создание заявки

Фрагмент из `AppointmentService`:

```java
Appointment appointment = new Appointment();
appointment.setPatientName(form.getPatientName());
appointment.setDoctor(doctorService.findById(form.getDoctorId()));
appointment.setMedicalService(medicalServiceService.findById(form.getMedicalServiceId()));
appointment.setStatus(AppointmentStatus.NEW);
return appointmentRepository.save(appointment);
```

Сервис создаёт заявку, связывает её с врачом и услугой, выставляет начальный статус и сохраняет в базе данных.

## Безопасность

В проекте реализованы следующие меры безопасности:

- пароли хранятся в виде BCrypt-хешей;
- вход и выход выполняются через Spring Security;
- доступ к защищённым страницам требует авторизации;
- административный раздел доступен только роли `ROLE_ADMIN`;
- формы защищены CSRF-механизмом Spring Security;
- пользовательский ввод проверяется на клиенте и сервере;
- доступ к данным выполняется через Spring Data JPA, без ручной конкатенации SQL-запросов.

## Ответы на контрольные вопросы

### 1. Что такое MVC?

MVC - архитектурный подход, разделяющий приложение на три части:

- Model - данные и бизнес-сущности;
- View - пользовательский интерфейс;
- Controller - обработка запросов и связь между моделью и представлением.

В проекте модели находятся в пакете `model`, контроллеры - в `controller`, а представления - в `src/main/resources/templates`.

### 2. Зачем нужна серверная валидация, если есть клиентская?

Клиентская валидация улучшает удобство пользователя, но её можно обойти. Серверная валидация обязательна, потому что только сервер может надёжно защитить приложение от некорректных или вредоносных данных.

### 3. Почему нельзя хранить пароль в открытом виде?

Если база данных будет скомпрометирована, открытые пароли сразу станут доступны злоумышленнику. Поэтому пароль должен храниться в виде криптографического хеша. В проекте используется BCrypt.

### 4. Что такое сессия?

Сессия - механизм хранения состояния пользователя между HTTP-запросами. После успешного входа Spring Security создаёт сессию и использует cookie `JSESSIONID` для определения авторизованного пользователя.

### 5. Чем отличается аутентификация от авторизации?

Аутентификация отвечает на вопрос "кто пользователь?", то есть проверяет логин и пароль. Авторизация отвечает на вопрос "что пользователю разрешено?", например доступна ли ему панель администратора.

### 6. Как в проекте ограничен доступ к админке?

Доступ к `/admin/**` ограничен правилом Spring Security:

```java
.requestMatchers("/admin/**").hasRole("ADMIN")
```

Обычный пользователь не может открыть административные страницы.

### 7. Что такое ORM?

ORM - технология сопоставления объектов приложения с таблицами базы данных. В проекте используется Hibernate ORM через Spring Data JPA. Классы `User`, `Doctor`, `Appointment` и другие являются JPA-сущностями.

### 8. Почему используется DTO для форм?

DTO отделяет данные формы от сущностей базы данных. Это упрощает валидацию, снижает риск случайного изменения лишних полей и делает код контроллеров понятнее.

### 9. Как предотвращается SQL-инъекция?

Проект использует Spring Data JPA и репозитории. Запросы формируются через параметры и методы репозиториев, а не через ручную конкатенацию строк SQL.

### 10. Что делает `DataInitializer`?

`DataInitializer` создаёт начальные данные при запуске приложения: администратора, врачей, услуги и объявления. Это позволяет сразу проверить работу приложения без ручного заполнения базы.
